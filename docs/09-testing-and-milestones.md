# 09 — Testing & Build Milestones

## Testing strategy by component class

The architecture was shaped to make most of the system testable without touching an LLM or even LilyPond; the test strategy follows that shape.

**Pure core (unit tests, no I/O).** `model/primitives/` (pitch/cents math, meter arithmetic, bar/beat↔offset round-trips — including additive meters, where the round-trip is trickiest), `notation/assemble.py`, `notation/chords.py`, `verification/midi_analysis.py`, `verification/transposition.py`, `performance/curves.py` and the interpretation transform, and every deterministic validator's logic. These are values-in/values-out: hand-constructed skeletons that must be rejected for gaps, crafted note lists containing known parallel fifths, motif entries that are and aren't valid tonal answers, `DynamicsPlan`s whose CC curves must hit given levels at given offsets. This layer carries the correctness guarantees, so it gets the densest tests — including property-style cases (every allowed meter × every rhythmic-cell length must sum correctly; surface→internal→surface round-trips are identity for every coordinate the surface can express).

**Golden fixtures.** `tests/fixtures/` holds small, hand-written artifacts with known properties: LilyPond fragments that are valid, that overfill a bar, that exceed a range, that omit bar checks; captured *real* LilyPond stderr for the warning parser; tiny multi-track MIDI files; golden score-MIDI→performance-MIDI pairs pinning the interpretation transform (given this score MIDI and these params, exactly these CC events). Fixture-driven tests pin contracts against reality rather than against our assumptions. When LilyPond is version-bumped, regenerating captured stderr is an explicit, reviewed step.

**Subprocess adapters (integration tests, real binaries, no LLM).** `LilypondAdapter` and `FluidsynthAdapter` run against the real tools in CI: compile a golden score, assert PDF + score MIDI appear with the channel invariant intact, assert bar-check warnings parse into the right structure; render a golden performance MIDI, assert audio duration is sane and CC dynamics audibly alter amplitude (RMS envelope check — crude, but it catches a SoundFont that ignores CC11). These tests are the version-drift tripwire.

**Graph logic (unit tests, all fakes).** `tests/fakes/` implements every protocol in memory: a `ScriptedGenerator` returning canned outputs (including scripted *failures* on attempt 1, success on attempt 2), a `ScriptedCritic`, a recording `ScoreRenderer`. Graph tests assert the loop mechanics: feedback routes to the right node, the motif layer is skipped when no materials are declared, budgets decrement per loop key, exhaustion raises `BudgetExhaustedError` with partials written, superseded feedback is cleared, fan-out covers every (section, voice), interpretation-parameter feedback re-renders without regenerating music. No patching anywhere — fakes enter through the factory.

**Live LLM verification (budgeted, manual/nightly, not CI-blocking).** Prompt quality can only be verified against real models. A small harness runs single capabilities live — "generate one 8-bar bass line in 7/8 against this skeleton, 10 trials" — and reports pass rates through the real validators. This is where prompt iteration happens, with measured feedback instead of vibes — and where **surface design is A/B-tested** (principle 2): alternative renderings of the same context (cells shown as notation vs. counting syllables; chord charts vs. prose harmony) compete on validator pass rates. Results are recorded in the repo so prompt and surface regressions are visible.

**End-to-end smoke (manual, per milestone).** One tiny piece — two sections, two voices, 5/4 and 7/8, one declared motif, one held-note crescendo — run through the full live pipeline. Its `RunConfig` and spec live in the repo as the canonical demo. The crescendo is in the smoke piece on purpose: it exercises the score/performance split end to end.

## Build milestones

Each milestone is a runnable slice verified before the next begins. Empirical unknowns are scheduled here as explicit checks; LLM-dependent milestones state their live-verification step.

**M0 — Skeleton & rendering boundary.** Repo scaffold, `model/` types including primitives, `LilypondAdapter` + `FluidsynthAdapter` with integration tests. Two empirical checks are pinned here because later design leans on their answers: (a) confirm the one-voice-one-channel invariant survives LilyPond's MIDI output for the SATB scaffold; (b) check whether quarter-tone accidentals reach MIDI as pitch bends — the answer decides how the microtonal door stays open, and is recorded in [03](03-musical-representations.md) either way. *Verified when:* a hand-written SATB LilyPond file in 7/8 (with one additive-meter bar) compiles to PDF + score MIDI + audio through the adapters, a deliberately broken one yields parsed bar-check warnings, and both empirical answers are recorded.

**M1 — Deterministic verification core.** `midi_analysis`, `transposition`, scaffolded fragment compiles, `validate_voice` and `validate_section` complete (including material-entry verification against hand-declared entries). *Verified when:* the full golden-fixture suite passes — every crafted-bad fragment rejected with a correctly targeted, rehearsal-note-worded `FeedbackItem`, every valid one accepted, valid and invalid tonal answers separated.

**M2 — Single-voice generation loop.** `llm/` package (prompts/schemas/parsers/service) for `generate_voice` only, plus the generate⇄validate loop in a minimal two-node graph. *Verified when:* the live harness shows an acceptable pass-within-budget rate (target: ≥80% of trials converge in ≤3 attempts) for single voices in 5/4 and 7/8, and at least one surface A/B (rhythmic-cell rendering) has been run and recorded.

**M3 — Structured layers.** `derive_style_pack`, `plan_structure`, `generate_motifs`, `generate_harmony` with their validators, wired sequentially with the conditional motif skip. *Verified when:* live runs produce plans, motifs, and skeletons passing deterministic validation on first or second attempt for three different style prompts — the Tool-choir spec, a fugue spec (exercising materials), and one deliberately dissimilar style (the genre-generality check).

**M4 — Full graph & performance stage.** Section assembly, cross-voice validation loop, score assembly, fan-out, `interpret_performance` with `DynamicsPlan`→CC implemented and identity elsewhere, `route_feedback` for validator items, budgets, partial-artifact failure path. *Verified when:* graph tests (fakes) cover all routing paths, and the e2e smoke piece completes live with all five artifacts consistent — and the held-note crescendo is audible in the rendered audio.

**M5 — Audio critique loop.** `GeminiCritic`, `CritiqueBrief` construction, LLM-backed `route_feedback.localize` with the cheapest-target-first policy, the stricter critique budget, interpretation-parameter adjustment path. *Verified when:* on the smoke piece, the critic produces localized, routable observations; a seeded-bad run (deliberately muddy voicing) gets caught and routed somewhere cheaper than `plan_structure`; and a "sounds flat" complaint demonstrably resolves through `InterpretationParams` without touching a note.

**M6 — The commission.** The Tool-inspired SATB piece, full spec, full pipeline. *Verified when:* success criteria 1–3 from [01](01-vision-and-scope.md) hold — and the score goes to a human musician for the judgment no validator owns.

Adjacent work discovered mid-milestone gets a tracked task, not an expanded milestone.
